# Project Plan: Tokens Studio Second-Screen Web Viewer

## 1. Project Overview
Build a Next.js (App Router) web application that acts as a two-way sync interface for Tokens Studio design tokens. The application must connect to Git repositories (GitHub or Azure DevOps) using a Personal Access Token (PAT), fetch raw `theme.json` and associated token files, resolve token aliases for visual rendering, allow inline editing, and push changes directly back to the specifically configured branch.

## 2. Tech Stack & Dependencies
*   **Framework:** Next.js (App Router, React 18+)
*   **Styling:** Tailwind CSS (for replicating the dark-mode Tokens Studio UI)
*   **State Management:** Zustand (crucial for managing the dual-state architecture)
*   **Token Processing:** `token-transformer` and `@tokens-studio/sd-transforms`
*   **Icons:** `lucide-react` (for UI elements)

## 3. Core Architecture Rules
*   **Dual-State Memory:** The frontend MUST maintain two completely separate states:
    *   `RawState`: The exact JSON string/object fetched from the Git provider. All UI edits must mutate *this* state to preserve deep aliases (e.g., `{brand.color.500}`).
    *   `ResolvedState`: A flattened JSON object generated by passing `RawState` through the token transformer. This is strictly read-only and used exclusively for rendering visual color swatches and computed values in the UI.
*   **Provider Agnosticism:** Backend API routes must dynamically format HTTP requests based on a `providerType` payload variable (`github` or `azure`).
*   **Direct Branch Commits:** Push operations must commit strictly and directly to the exact branch string provided in the sync configuration. Do not implement Pull Request generation workflows.

## 4. Implementation Phases

### Phase 1: Setup & State Initialization
1.  Initialize the Next.js App Router project with Tailwind CSS.
2.  Install dependencies: `npm install zustand token-transformer @tokens-studio/sd-transforms lucide-react`.
3.  Create a Zustand store (`store/useTokenStore.ts`) containing:
    *   `credentials`: Object storing Provider, Org/Owner URL, Repo Name, Branch, Path, and PAT.
    *   `rawTokens`: Object storing the unresolved JSON.
    *   `resolvedTokens`: Object storing the flattened JSON.
    *   `setCredentials`, `setRawTokens`, `setResolvedTokens`, `updateSingleToken` actions.

### Phase 2: Git Provider API Routes (Read)
1.  Create an API route `app/api/git/fetch/route.ts` (POST).
2.  Accept credentials payload from the client.
3.  Implement conditional fetching logic:
    *   **If GitHub:** Use `fetch('https://api.github.com/repos/${owner}/${repo}/contents/${path}?ref=${branch}')`. Pass PAT in `Authorization: Bearer` header. Decode base64 response.
    *   **If Azure:** Use `fetch('https://dev.azure.com/${org}/${project}/_apis/git/repositories/${repo}/items?path=${path}&versionDescriptor.version=${branch}&api-version=7.0')`. Pass PAT in `Authorization: Basic [base64(:PAT)]` header.
4.  Return the parsed raw JSON to the client.

### Phase 3: Token Processing Engine
1.  Create a utility function `utils/transformTokens.ts`.
2.  Import the raw JSON fetched from Phase 2.
3.  Run the raw JSON through `token-transformer` to resolve math, cross-file references, and aliases.
4.  Dispatch the output to the Zustand `resolvedTokens` state.
5.  Set up a `useEffect` hook in the main application layout that automatically re-runs this transformer utility whenever `rawTokens` changes.

### Phase 4: User Interface Construction
1.  **Sidebar (`components/Sidebar.tsx`):** Render a list of Token Groups (Semantic, Components, Themes) parsed from the keys of the JSON object.
2.  **Data Table (`components/TokenTable.tsx`):** 
    *   Render a grid layout matching the Tokens Studio interface.
    *   Columns: Token Name, Dark Value, Light Value.
    *   Map through the `resolvedTokens` to render a circular `<ColorSwatch>` component for visual feedback.
    *   Render `<input>` fields for the token values. **CRITICAL:** Bind the `onChange` event of these inputs to the `updateSingleToken` Zustand action, mutating the `rawTokens` state (not the resolved state) to preserve aliases.

### Phase 5: Git Provider API Routes (Push)
1.  Create an API route `app/api/git/push/route.ts` (POST).
2.  Accept the mutated `rawTokens` JSON, commit message, and credentials payload.
3.  Implement conditional pushing logic strictly targeting the configured branch:
    *   **If GitHub:** Fetch the latest commit SHA for the branch, post a new blob with the updated JSON string, create a new tree, create a commit, and update `refs/heads/${branch}`.
    *   **If Azure:** Construct a push payload using the `_apis/git/repositories/${repo}/pushes` endpoint. Specify the `targetRefName` as `refs/heads/${branch}` and include the new JSON string in the `changes` array as an `edit` operation.
4.  Add a "Push to ${branch}" button in the UI that triggers this route and displays a success/error toast notification upon completion.

### Phase 6: Vercel Deployment & Production Readiness
1.  **Zero-Config Deployment:** Ready for direct import into Vercel with standard Next.js App Router preset.
2.  **Serverless API Runtime:** Node.js serverless execution for `/api/git/*` routes handling payload sizes up to 4.5 MB.
3.  **Security Architecture:** Personal Access Tokens (PATs) remain purely client-held in session/local storage, passed securely over HTTPS directly to the serverless proxy endpoints.
4.  **Optional Default Env Vars:** Support optional `NEXT_PUBLIC_DEFAULT_*` env vars in Vercel project settings for pre-filling team repository coordinates.
